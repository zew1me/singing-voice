# Repository Guidelines

## Project Structure & Module Organization
- `src/singing_voice/`: core Python package with CLI (`cli.py`), preprocessing (`preprocess.py`), stitching (`stitch.py`), scoring (`score.py`, optional models in `score_models.py`), the test-set runner (`bench.py`), manifest helpers, and RunPod submission utilities. Keep new modules within this package to ensure Typer entry points stay discoverable.
- `runpod_worker/`: GPU-only Seed-VC worker (`engine.py`, `handler.py`, Dockerfile built by RunPod from this repo). Keep its job contract in step with `singing_voice.transport` and `singing_voice.convert_client`.
- `testsets/`: test-set JSON files naming fixed excerpts; their audio lives in git-ignored `test_files/`.
- `working/`: scratch space for manifests/audio generated by `svtool`. Never commit outputs—add new temp directories under `working/<session_timestamp>/`.
- `pyproject.toml`: single source of dependency truth. Update optional extras instead of ad-hoc requirements files.

## Build, Test, and Development Commands
- `uv tool install 'lefthook==2.2.2' && lefthook install`: enable the staged whitespace check and locked pytest pre-push hook.
- `./scripts/runpod-preflight [revision]`: opt-in `linux/amd64` image build and offline import smoke test from a Git commit.
- `uv venv && source .venv/bin/activate`: create/activate the local virtualenv.
- `uv pip install -e .[runpod]`: install the editable package plus optional HTTP client deps.
- `svtool preprocess input.wav --workdir working`: run Step A locally; outputs manifest JSON.
- `svtool convert vocal.wav --reference voice.wav --duration-s 30`: convert on the RunPod endpoint (`RUNPOD_API_KEY`, `RUNPOD_ENDPOINT_ID`).
- `svtool stitch converted_manifest.json --output working/final.wav`: run Step C locally.
- `svtool score working/<out>.wav`: score a conversion (`uv pip install -e '.[score]'` for the timbre and words sections).
- `svtool bench run testsets/m1.json --label <name>` then `svtool bench compare <run-a> <run-b>`: judge a pipeline change on the fixed test set.

## Coding Style & Naming Conventions
- Python 3.10+, follow PEP 8 (4-space indent, snake_case functions). Prefer dataclasses for config payloads and keep new manifests in `manifests.py`.
- All CLI options should expose explicit units (e.g., `--chunk-seconds`). Keep generated files out of repo by defaulting to `working/`.

## Testing Guidelines
- `uv run pytest`. Tests live under `tests/` and cover pure helpers, scoring on synthetic sung lines (`tests/conftest.py:sung`) with fake models, and the worker contract with a fake engine; check the model itself with a real conversion, and judge changes with `svtool bench`.
- Use pytest naming (`test_<module>.py`) and keep fixtures deterministic by seeding NumPy.

## Commit & Pull Request Guidelines
- Commit messages: short imperative summary (`Add stitch crossfade control`). Reference issue IDs when applicable.
- Pull requests should describe the affected pipeline step (A/B/C), list new commands or flags, and mention manual verification (e.g., sample WAV run). Include before/after audio artifacts via external links when relevant.
